# Story 1.1 — Client readiness fixes (F01–F08)

**Status:** InReview
**Source:** [docs/reviews/2026-10-01-prontidao-clientes.md](../reviews/2026-10-01-prontidao-clientes.md)
**Base commit:** `a69ef51`

## Story

As a DBA distributing postgres_dba to client environments, I want the index
recommendations, role-management routines, menu input handling, generator and
`a2` report to behave correctly, so that following the tool's output cannot
remove uniqueness guarantees, grant unintended privileges, leak passwords or
run unexpected SQL.

## Acceptance criteria

1. **F01/F05 — index semantics (`i2`, `i3`, `i5`).** An index B is reported
   as redundant to A only when, on the same table, with the same access method,
   predicate and expressions:
   - B's key columns, operator classes, collations and ordering options
     (ASC/DESC, NULLS FIRST/LAST) are a prefix of A's (an exact match for
     non-btree methods), compared as arrays, not as text;
   - B's INCLUDE columns are contained in A's columns;
   - if B is unique, A is an immediate unique index on exactly the same key
     columns with the same NULLS [NOT] DISTINCT behaviour;
   - B is not a primary key and does not back a constraint.
   Of two equivalent indexes, exactly one (the newer) is suggested. `i3`
   groups only indexes that are fully identical, including uniqueness and
   ordering. `i5` never emits a DROP for a unique or constraint-backed index
   that has no unique equivalent, and quotes index names correctly.
2. **F02 — `u2`** always applies both attribute values explicitly
   (`SUPERUSER`/`NOSUPERUSER`, `LOGIN`/`NOLOGIN`).
3. **F03 — `u1`/`u2`** accept only an explicit list of yes/no answers
   (English and Portuguese) and abort without changes on any other answer.
4. **F04 — passwords** come from a cryptographically strong source
   (`gen_random_uuid()`, backed by `pg_strong_random()`), are unaffected by
   `setseed()`, and never appear in a server message (`RAISE` of any level).
   The password is delivered to the client only through psql output.
5. **F06 — input handling.** Menu choice, role name, `a2` seconds and `k1`/`k2`
   PID are passed as escaped psql literals (`:'var'`); numeric inputs are
   validated before any administrative function is called.
6. **F07 — `init/generate.sh`** resolves output paths inside the repository,
   writes to temporary files and replaces the outputs atomically; it never
   touches files in the caller's directory and it fails on errors.
7. **F08 — `a2`** shows a non-negative `duration` (`clock_timestamp() -
   query_start`), ordered longest first.
8. Behaviour tests reproducing every finding run in CI on PostgreSQL 14–18.
9. README documents the role-management changes, input rules, the `pg_monitor`
   diagnostic profile and which reports change state.

## Dev notes

- Local evidence (2026-10-06, Podman, no network): smoke suite 33 reports × {superuser, pg_monitor} × {normal, wide}
  with 0 failures and `test/behavior.sh` all passing on PostgreSQL 14, 16 and 18. PostgreSQL 15 and 17 are covered by CI only.
- The same `test/behavior.sh` run against the original code (`a69ef51`) fails 23 checks, covering F01–F08.
- Decision: `u1`/`u2`/`k1`/`k2` now run in CI, but only inside `test/behavior.sh`, against fixture roles and a
  backend the test starts. This replaces the earlier rule that they never run in automation; the review required
  behaviour tests for them.
- Residual risk (documented in README): the executed CREATE/ALTER ROLE contains the password, so
  `pg_stat_statements.track = all` or `auto_explain` with nested statements can capture it.
